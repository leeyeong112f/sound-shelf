# 볼트 다중 Mac 동기화 설계

> 2026-07-17. 두 대의 Mac에서 Sound Shelf를 동시에 켜둔 채 태그 등 라이브러리 변경사항을
> 서로 반영하기 위한 설계. 볼트는 Google Drive 스트리밍 폴더에 위치한다.
> 기준 커밋: `700b471`

## 배경

### 지금 어떻게 동작하는가

사용자 편집 항목(제목, 태그, 메모, 즐겨찾기, 별점, 키 분석)은 볼트 안
`<볼트>/.sound-shelf/metadata.json`에 저장된다 (`src/vault-storage.js`의 `saveMetadata`).
폴더 순서는 같은 디렉터리의 `folder-order.json`에 저장된다.
볼트가 Google Drive에 있으므로 **이 파일들 자체는 이미 두 Mac 사이에 동기화된다.**

로컬 SQLite 캐시(`vault-cache/<vaultId>.sqlite`)는 ffprobe 기술 정보만 담으므로
Mac별로 따로여도 무방하다. 단축키와 미리듣기 볼륨은 로컬 userData의 JSON db에만 있다.

### 무엇이 문제인가

1. **읽기가 시작 시 1회뿐이다.** `loadMetadata()`는 `activateVaultNow()` 안에서만 호출된다
   (`src/main.js:278`). 즉 앱 시작 또는 수동 볼트 '열기' 때만 읽는다. 한쪽 Mac에서 태그를
   고쳐도 다른 Mac은 재시작 전까지 알지 못한다.

2. **감지하지 않는다.** 폴더 감시자가 `.sound-shelf` 경로를 의도적으로 무시한다
   (`src/main.js:838`). Google Drive가 파일을 내려받아도 앱은 눈치채지 못한다.

3. **통째로 덮어쓴다 (데이터 유실).** `saveDb()`는 메모리의 사운드 목록 전체를 스냅샷으로
   써버린다 (`src/main.js:397-401`). 두 Mac이 동시에 켜져 있으면 나중에 저장한 쪽이
   상대방의 편집을 **해당 사운드뿐 아니라 전부** 날린다. 오래된 상태로 떠 있던 Mac이
   볼륨 하나만 바꿔도 상대의 몇 시간치 작업이 사라질 수 있다.

4. **Drive 충돌 사본.** 두 기기가 같은 파일에 동시에 쓰면 Google Drive는 충돌 사본
   (`metadata (1).json`)을 만들거나 한쪽을 조용히 버린다. 앱 계층에서 아무리 잘 병합해도
   Drive 계층의 유실은 막을 수 없다.

즉 현재는 "동기화가 안 되는" 상태가 아니라 **"동시에 켜면 데이터가 유실될 수 있는"** 상태다.

## 요구사항

확정된 사항:

| 항목 | 결정 |
|------|------|
| 사용 패턴 | 두 Mac을 **동시에 켜두고** 번갈아 사용 |
| 반영 속도 | 수 초~수십 초 (Drive 동기화 지연 수준). 새 서버·LAN 계층 없음 |
| 동기화 대상 | 사운드 메타데이터(제목·태그·메모·즐겨찾기·별점), 폴더 순서, 미리듣기 볼륨 |
| 충돌 규칙 | **사운드 단위 last-writer-wins** (나중에 고친 쪽이 이김) |
| 기기 수 | 2대 (3대 이상은 범위 밖이나 설계상 자연히 확장됨) |

동기화 대상이 **아닌** 것:

- 사운드 파일 자체의 이동·이름변경·삭제 — Google Drive가 이미 동기화하고, 앱에 재연결
  (relink) 로직이 있다.
- **단축키(`shortcuts`)** — 사용자 결정. Mac마다 키보드 구성이 다를 수 있어 각자 독립적으로
  둔다. 로컬 `db.settings`에 그대로 남긴다.
- `watchedFolders`, `currentVaultRoot` 등 경로 설정 — Mac마다 달라야 한다.
- 키 분석 결과(`keyAnalysis`) — 사용자가 동기화 대상으로 고르지 않았다. 다만 사운드
  레코드에 실려 다니므로 결과적으로는 함께 전파된다. 이를 막기 위해 별도 처리를 넣지는
  않는다 (막으면 오히려 저장될 곳을 잃는다).
- 로컬 SQLite 기술 캐시 — Mac별 파생 데이터.

## 접근법 비교

| 안 | 내용 | 결론 |
|----|------|------|
| A | `metadata.json`을 공유 파일로 유지하고 저장 직전 재읽기·병합 | **반려.** 두 Mac이 여전히 같은 파일에 쓴다. Drive 충돌 사본과 read-modify-write 경합이 남는다 |
| B | **각 Mac이 자기 편집 파일에만 쓰고, 읽을 때 병합** | **채택** |
| C | 볼트에 공유 SQLite DB | **반려.** SQLite 파일 잠금은 Drive 같은 동기화 파일시스템에서 동작하지 않아 DB 손상 위험이 실재한다 |

B안의 핵심: **두 Mac이 같은 파일을 절대 건드리지 않으면 Drive는 충돌을 만들 수 없다.**

대가: 파일이 늘고 읽기 경로에 병합 단계가 생겨 A안보다 코드가 늘어난다. 시계가 크게
어긋나면 "나중"의 판정이 틀어질 수 있으나, 같은 사용자의 NTP 동기화된 Mac 두 대라면
실무상 문제가 되지 않는다.

## 설계

### 모듈 분리

`src/main.js`는 이미 1,900줄이 넘는다. 동기화까지 넣으면 감당이 안 되고, 병합 로직을
테스트할 수도 없다. 따라서 **`src/vault-sync.js`** 를 새로 만든다.

- **무엇을 하는가**: 베이스 스냅샷과 편집 파일들을 받아 병합된 상태를 계산한다.
- **어떻게 쓰는가**: `mergeVaultState(base, editSources)` → 병합 결과. **순수 함수**로,
  파일 입출력도 시계도 모른다.
- **무엇에 의존하는가**: 없음 (Node 내장만).

`main.js`는 파일을 읽어 넘기고 결과를 받아 쓰기만 한다. 이 경계 덕분에 병합 규칙을
Electron 없이 단위 테스트할 수 있다.

### 볼트 안 구조

```
<볼트>/.sound-shelf/
	vault.json          ← 볼트 신원. 저장할 때마다 건드리지 않도록 변경
	metadata.json       ← 베이스 스냅샷. 사실상 읽기 전용이 됨
	folder-order.json   ← 기존 유지 (베이스)
	edits/
		<machineId>.json   ← 이 Mac만 쓰는 파일
```

`machineId`는 Mac마다 한 번 생성해 **로컬 userData에만** 보관한다 (`db.settings.machineId`).
볼트에 넣으면 그 값 자체가 동기화되어 두 Mac이 같은 ID를 갖게 되므로 반드시 로컬이어야 한다.
`activateVaultNow()`의 `preserveSettings` 경로로 보존되며, 없으면 `loadDb()` 시점에 생성한다.

### 편집 파일 형식

그 Mac이 **실제로 손댄 것만** 들어간다.

```json
{
	"type": "sound-shelf-edits",
	"schemaVersion": 1,
	"vaultId": "<볼트 UUID>",
	"machineId": "a1b2c3...",
	"machineName": "Mac Studio",
	"updatedAt": "2026-07-17T12:00:00.000Z",
	"sounds": {
		"<soundId>": {
			"updatedAt": 1752710400000,
			"id": "<soundId>",
			"relativePath": "액션/문열림.wav",
			"fileName": "문열림.wav",
			"title": "문 열림",
			"tags": ["액션", "실내"],
			"notes": "",
			"favorite": true,
			"rating": 4,
			"createdAt": 1752600000000,
			"modifiedAt": 1752500000000,
			"size": 482910,
			"contentHash": "...",
			"keyAnalysis": null
		}
	},
	"folderOrder": { "updatedAt": 1752710400000, "order": ["액션", "자연"] },
	"settings": { "updatedAt": 1752710400000, "previewVolume": 0.8 }
}
```

- 사운드 레코드는 **기존 `portableSound()`가 만드는 형태 그대로에 `updatedAt`만 얹은
  것**이다 (`src/main.js:197`). 일부 필드만 담으면 안 되는 이유가 있다. `metadata.json`을
  더 이상 쓰지 않으므로 편집 파일이 **유일한 영구 저장소**가 되고, 레코드가 부분적이면
  키 분석 결과나 새로 발견된 파일의 `createdAt`·`contentHash`가 저장될 곳을 잃어
  재시작 시 사라진다. 전체 형태를 담으면 이 문제가 없고 기존 `portableSound()`를
  그대로 재사용할 수 있다.
- 사운드는 **`id`를 키**로 한다. `relativePath`는 재연결·복구용 보조 정보다.
- **삭제는 표식(tombstone)으로 기록한다.** `{ "updatedAt": 1752710400000, "deleted": true }`
  형태이며 병합에서 이 기록이 이기면 결과에서 제외한다. 표식이 없으면 베이스
  `metadata.json`에 남은 레코드 때문에 삭제한 사운드가 재시작 시 되살아난다
  (`metadata.json`을 더 이상 쓰지 않으므로 삭제가 베이스에 반영될 길이 없다).
- `settings`에는 **미리듣기 볼륨만** 넣는다. 단축키(`shortcuts`)와 경로 설정
  (`watchedFolders`, `currentVaultRoot`)은 로컬 `db.settings`에 남겨 Mac마다 독립적으로
  둔다.
- `sounds[].updatedAt`은 **그 편집이 실제로 일어난 시각**이지 파일을 쓴 시각이 아니다.
  이 구분이 병합의 정확성을 좌우한다.

### 병합 규칙

`metadata.json`을 베이스로 깔고 `edits/`의 모든 파일을 얹는다.

1. 사운드 ID별로 `updatedAt`이 **가장 큰 기록이 이긴다** (사운드 단위 last-writer-wins).
2. `updatedAt`이 동률이면 `machineId` 사전순으로 결정한다. 두 Mac이 각자 계산해도
   **반드시 같은 결론**에 도달해야 하기 때문이다.
3. 이긴 기록이 **삭제 표식이면 결과에서 제외**한다.
4. 폴더 순서와 설정도 같은 방식으로 가장 최신 것 하나가 이긴다.
5. 병합 결과에 승리한 기록의 `updatedAt`을 그대로 보존한다 (재병합 시 수렴 보장).

베이스(`metadata.json`)의 사운드에는 `updatedAt`이 없다. 이를 `0`으로 취급하면 어떤 편집도
베이스를 이기므로 규칙이 단순해진다.

핵심 성질: 각 Mac은 **자기가 만진 사운드만** 기록하므로, 한쪽이 오래된 상태로 몇 시간
떠 있어도 자기가 안 건드린 사운드에 대해서는 아무 주장도 하지 않는다. 현재의 "통째로
덮어쓰기" 유실이 구조적으로 불가능해진다.

### 쓰기 흐름 (내 변경 → 다른 Mac)

**변경 감지는 차이 비교(diff)로 한다.** `saveDb()` 호출 지점이 코드 전체에 30곳 있어
(태그·이름변경·일괄수정·카테고리 이동·키 분석·삭제 등) 각 편집 지점에서 손으로
`updatedAt`을 찍게 하면 하나만 빠뜨려도 그 편집이 조용히 동기화되지 않는다. 대신:

1. 마지막으로 병합해 알고 있는 공유 상태를 **베이스라인**으로 메모리에 들고 있는다.
2. `saveDb()`에서 현재 `db.sounds`를 베이스라인과 비교한다.
   - 사용자 편집 필드가 다르거나 베이스라인에 없는 사운드 → `updatedAt = Date.now()`를
     찍어 내 편집 파일에 넣는다 (새로 발견된 사운드도 이 경로로 들어간다).
   - 베이스라인에 있는데 현재 없는 사운드 → **삭제 표식**을 넣는다.
   - 나머지는 건드리지 않는다.
3. 볼트에는 **내 `edits/<machineId>.json` 하나만** 쓴다. 기존 `writeJsonAtomic`
   (임시 파일 → rename)을 그대로 사용해 Drive가 반쯤 쓰인 파일을 올리지 않게 한다.
4. 베이스라인을 방금 쓴 상태로 갱신한다.
5. 로컬 SQLite 기술 캐시와 로컬 db는 지금처럼 계속 쓴다.

이 방식의 이점은 **호출부를 한 곳도 고치지 않으면서 누락이 원천적으로 불가능**하다는 것이다.
사운드 2,185개에 대한 필드 몇 개 비교는 1밀리초 미만이라 비용도 무시할 수 있다.

**`metadata.json`은 평상시 아무도 쓰지 않는다.** 새로 발견된 사운드도 편집 파일에 들어간다.
`saveMetadata()`가 매번 `vault.json`의 `updatedAt`을 갱신하던 것도 공유 쓰기이므로
정상 경로에서 제거한다. 결과적으로 **정상 동작 중 공유 파일 쓰기는 0번**이 되고,
Drive가 충돌 사본을 만들 이유가 사라진다.

편집 파일이 무한정 커지지 않느냐는 우려에 대해: 레코드가 사운드 전체 형태이므로 하나에
약 300바이트, 2,185개 전부를 편집해도 1 MB 미만이다. 최악의 경우가 현재 `metadata.json`
크기와 같은 수준이라는 뜻이다. 접기(compaction)는 필요해지면 나중에 붙인다 (YAGNI).

### 읽기 흐름 (다른 Mac의 변경 → 나)

1. **7초마다** `edits/` 안에서 내 것이 아닌 파일들의 mtime과 size만 확인한다
   (`stat` 두어 번이라 비용이 없다시피 하다).
2. 바뀐 파일이 있으면 그 파일만 다시 읽어 병합한다.
3. 실제로 달라진 사운드가 있을 때만 렌더러에 `library-updated`를
   `updateReason: 'remote-sync'`로 보낸다.
4. 렌더러는 "다른 Mac의 변경 사항을 반영했습니다" 토스트를 띄운다. 이 경로는 이미 폴더
   자동 감지가 사용 중인 검증된 경로다.

**`fs.watch`를 쓰지 않는 이유**: Google Drive의 가상 파일시스템이 macOS FSEvents를
제대로 발생시키는지 보장할 수 없다. 7초 폴링은 확실히 동작하고 요구 속도에 부합한다.
어차피 Drive가 파일을 내려받는 지연이 훨씬 크다.

**시작 로직과의 관계**: 폴링은 `startupLoading`이 끝난 뒤 시작하고, 기존 볼트 활성화
큐(`vaultActivationQueue`)에 얹어 스캔과 병합이 겹치지 않게 직렬화한다.

**진행 중인 로컬 편집과의 관계**: 로컬의 저장되지 않은 편집은 `updatedAt`이 더 최신이므로
병합에서 자연히 이긴다. 별도 처리가 필요 없다.

### 오류 처리

| 상황 | 처리 |
|------|------|
| 반쯤 동기화된 파일 (JSON 파싱 실패) | 그 파일만 이번 회차에서 건너뛰고 다음 폴링에 재시도. 로컬 상태는 절대 버리지 않는다 |
| 충돌 사본이 그래도 생김 (`mac-studio (1).json`) | `edits/`의 `*.json`을 **전부** 병합 소스로 취급한다. 무시하면 그 안의 편집이 유실되므로 읽어서 합치는 편이 안전하다 |
| 볼트가 연결되지 않음 | 기존 `connected` 검사로 폴링을 건너뛴다. 오프라인 편집은 내 파일에 쌓였다가 Drive 연결 시 자연히 올라간다 |
| 편집 파일 쓰기 실패 | 로그를 남기고 다음 `queueSave()`에 재시도한다 |
| 시계 어긋남 | 동률 시 `machineId` 사전순 결정으로 두 Mac이 갈라지지 않게 한다 |
| `vaultId` 불일치 | 기존 `loadMetadata()`와 같이 거부한다 |

### 테스트

현재 저장소에는 테스트 프레임워크가 없고 `npm run check`는 문법 검사뿐이다. 병합을 순수
함수로 뽑는 이유가 여기에 있다.

**단위 테스트** — `node:test`로 `npm test`를 추가한다 (의존성 추가 없음). `mergeVaultState()`에 대해:

- 새 `updatedAt`이 오래된 것을 이긴다
- 한쪽이 만지지 않은 사운드는 덮이지 않는다 (핵심 회귀 방지)
- 동률일 때 결정적이다 (`machineId` 사전순)
- 병합 순서를 바꿔도 같은 결과가 나온다 (수렴)
- 깨진 편집 파일은 무시하고 나머지는 병합한다
- 폴더 순서·설정도 최신 것이 이긴다
- 베이스에만 있고 아무도 편집하지 않은 사운드는 그대로 살아남는다
- 삭제 표식이 이기면 결과에서 빠지고, 표식보다 새로운 편집이 있으면 되살아난다

**통합 테스트** — userData를 각각 다르게 준 Electron 인스턴스 두 개를 **로컬 임시 폴더**
볼트에 붙여, A에서 태그를 고치고 B에 10초 안에 반영되는지 확인한다. 시작 속도 수정 때
사용한 격리 실행 방식을 그대로 쓴다.

**실제 Google Drive 볼트로는 테스트하지 않는다** — 사용자의 진짜 데이터이기 때문이다.

## 마이그레이션

기존 볼트는 그대로 열린다. 첫 실행 시 `metadata.json`에 사운드 2,185개가 베이스로 있고
`edits/`는 비어 있다. 사용자가 무언가를 편집하면 그때부터 편집 파일에 레코드가 하나씩
쌓인다. 스키마 변경도 데이터 이전도 필요 없다.

내보내기·백업(`backupPortableMetadata`)은 **병합된 상태**를 쓰도록 바꾼다. 그래야 백업이
편집 내용을 포함한다.

**백업 복원의 의미 (확정된 제품 결정, 2026-07-18):** 백업 복원은 베이스를 되돌리지만
`edits/`의 편집 기록은 남으므로, **복원 이후에도 그보다 새로운 편집(태그·별점 등)이
이긴다.** 즉 "어제 백업으로 롤백"이 그 사이의 편집을 되돌리지 않는다. 다중 Mac에서는
복원이 다른 Mac의 최근 작업을 지우면 안 되므로 이것이 안전한 기본값이며, 의도된
동작이다. 편집까지 되돌리는 복원이 필요해지면 `edits/` 정리를 포함하는 별도 기능으로
추가한다.
